# ADR-0059 — Canonical Graphics-Card BuildKit-to-PCIe x16 Retention Assembly Handoff

**Status:** Accepted for source/domain/scene/input/full-regression, exact-head macOS/Windows native and technical-CI gates; source/docs CI, final canonical/large local checkpoint, real-human session, healthy physical USB and administrative closure pending<br>
**Date:** 26 August 2026<br>
**Scope:** Issue #99, child of Epic #10

## Context

Issues #68 through #87 stage the exact ten reserved custom-PC components in component-specific capacity-one BuildKit slots. Issues #89, #91, #93, #95 and #97 then move the same motherboard, CPU, DDR5, M.2 and processor cooler into their existing Assembly authorities while preserving the immutable ten staging receipts and live reservation/allocation lineage.

Issue #59 already owns deterministic single-GPU PCIe x16 compatibility, keyed orientation, guided seat, slot latch, rear-bracket fastener, retained-removal block, unretain, detach, clearance, obstruction and replay semantics. Issue #79 stages the canonical reserved GPU; Issue #63 separately owns PCIe GPU power-cable route authority. The missing boundary is a reservation-safe bridge from the exact GraphicsCard BuildKit custody to the existing Issue #59 slot after the full live prerequisite Assembly chain is proven, without activating or mutating Issue #63.

A second Inventory, shadow GPU/slot/latch/bracket authority, regenerated identity or implicit power-cable route would split truth. A presentation-only pickup would also be invalid: the same serialized Unity instance must move through authoritative custody and recover fail closed after projection failure or current obstruction.

## Decision

- Resolve only the exact owned work order's canonical `GraphicsCard` line and full `LineId`, `ProductId`, serialized `ItemId`, `ReservationId`, parent allocation and original staging-receipt tuple. Ordinal, display-name, component-only and value-equivalent matches cannot acquire authority.
- Require the historical exact ten-receipt `10/10` aggregate plus live exact Issue #89/#91/#93/#95/#97 receipts. The motherboard must be Workbench-owned and `SeatedSecured`; CPU ProcessorSocket-owned and `ProcessorRetained`; DDR5 exact A2 MemorySlot-owned and `MemoryModuleRetained`; M.2 exact primary-slot-owned and captive-screw secured; cooler ProcessorCoolerSlot-owned and `CoolerRetained`.
- Require the configured GraphicsCardSlot to be managed, capacity one, PCIe x16 compatible, foreign-container-free and `EmptyOpen`, with exact latch/rear-bracket/fastener topology. Full hands, occupied slot, stale authority/revision, wrong prerequisite, invalid orientation, current obstruction or overflow fail closed.
- Use a stable GPU assembly-handoff operation identity distinct from staging, all prior component handoffs, Issue #59 seat/retention operations and Issue #63 cable operations. Immediate and delayed replay return the same immutable receipt without a second custody or revision change.
- Add only the narrowly registered GraphicsCard BuildKit → `ActorHands` release. Subsequent reversible transfer remains the existing exact GraphicsCardSlot ↔ `ActorHands` Assembly path; generic reserved transfer, checkout and world drop remain closed.
- Preserve reservation and parent allocation through pickup, seat, latch/rear-bracket retain, unretain and detach. Preserve all ten staging receipts and visible `10/10` history while tracking current custody separately. The other four uninstalled BuildKit components and installed motherboard/CPU/DDR5/M.2/cooler states remain unchanged.
- Preserve Issue #63 independently: PCIe GPU power-cable item/product/container/state/revision/receipt/operation authority is byte-for-byte unchanged across BuildKit→hands→seat→retain→unretain→detach. If the cable is already routed, unretain/remove remains fail closed; this handoff never creates a route.
- Reuse Issue #59 compatibility, orientation, support/chassis/cooler clearance, obstruction, preview-equals-commit, latch/rear-bracket and replay rules. This handoff authorizes that authority; it does not recreate or relax it.
- Commit authoritative custody before changing parent/pose/physics/visibility. Projection failure recovers the same Unity component and stable ItemId to the authoritative hands/slot pose; duplicate, ghost and loss counts remain zero. Recovery rechecks current obstruction and fails closed until the seat is physically clear.
- Keep retained removal blocked. Keep motherboard unsecure/detach, CPU retention opening and DDR5/M.2/cooler custody/state changes blocked while the GPU is seated or retained.
- Keep BuildKit pickup, guided seat, retention, detach, cable route and generic drop edges single-consumer across keyboard/mouse and gamepad. Range, focus, line of sight, pause/focus neutralization, release/repress and held/co-edge rules remain fail closed.
- Bind acceptance to exact technical commit/tree, targeted and full test XML, macOS and Windows native artifacts, binary/procedure hashes, graceful cleanup and package readback. Runtime acceptance requires one r50 readiness marker with `graphics-card-assembly-handoff=ready`, one exact GPU Assembly handoff success marker, zero failure/diagnostic/fatal markers and zero player/Unity/task/validation-PowerShell residue.
